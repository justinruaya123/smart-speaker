Status: governing project requirements and implementation gap map. Baseline inspected on 2026-09-20; the later E12 implementation and regression update is recorded below. Read this file before proposing an experiment, expanding data, designing a benchmark or declaring a model complete. See [EXPERIMENTS.md](EXPERIMENTS.md) for the consolidated experiment directory and linked detailed evidence. Read [AGENTS.md](AGENTS.md) for execution, provenance, experiment isolation and maintenance rules.

## 1. Core problem

Build a tiny Voice Command Model (VCM) that understands common spoken smart-device commands, including their required parameters, entirely on a Raspberry Pi 4 or 5 in real time. The model must operate standalone, with no cloud model calls, no LLM and no ASR/STT pipeline of any kind.

The engineering motivation is to avoid the footprint and computation of a general transcription system when the task is a bounded set of commands. This is a project objective, not a claim that every ASR architecture is too large for every device. Measure the complete deployed solution, including preprocessing, all acoustic heads, decoding, catalogs and dependencies. Renaming ASR to STT does not reduce its footprint or satisfy the VCM requirement.

The central research question is: **How small can a direct voice-command model be while reliably recognizing the target intents and parameters, rejecting unsupported speech, and meeting measured real-time limits on an RPi4/5?**

The required result is a valid structured command or explicit rejection/clarification, not merely a transcript, isolated keyword, high pooled accuracy or plausible device action. A family-only classifier with unresolved required parameters is an incomplete command recognizer.

## 4. Non-negotiable inference contract

1. **On-device recognition:** microphone/file -> mono 16 kHz PCM -> local VAD -> VCM intent and required finite parameters -> typed validation -> command JSON or explicit abstention. No cloud-based recognition, external model API or LLM in this path.
2. **VCM authority:** no transcript parser, parameter reader or secondary model may select a family, rescue a rejected family or bypass its confidence/validity gates. Joint or auxiliary finite acoustic heads may form part of the VCM; count their entire cost.
3. **Strict no-ASR rule:** no ASR/STT transcription pipeline is allowed, whether cloud or local, general or narrow, mandatory or optional, including brightness/name parameter readers and fallbacks. Audio must produce VCM command decisions/finite parameters rather than a transcript that is parsed into a command. Deterministic validators may validate VCM outputs but cannot invent an unrecognized value. Calling a transcriber a keyword, phonetic or parameter reader does not create an exception. Assess finite acoustic cue heads by what they actually compute; a CTC loss or a small vocabulary alone proves neither compliance nor noncompliance.
4. **Honest rejection:** reject/clarify unsupported, unknown, missing, malformed, conflicting or ambiguous input. Report false accepts and complete-command recall as well as precision; rejecting everything does not satisfy the assignment.
5. **No hidden costs:** include every shipped model, frontend, decoder, vocabulary/catalog and dependency in resource accounting. Development tools or agent assistance are not runtime components. "No LLM" applies to the delivered inference/demo path; it does not ban LLM-assisted coding of this repository.
6. **Recognition versus action:** current code emits commands and does not execute devices. Future demo action bindings need explicit scope, known targets and deterministic local handling. Do not add Spotify, Home Assistant, messaging or other integrations merely because a use case is listed here.
7. **Offline meaning:** recognizing a weather/search/call request is different from fetching live weather, searching the web or placing a call. The VCM cannot infer fresh external facts. Define the demo's local behavior and declare any unavailable information; do not claim open-ended answers or external actions from intent detection. Recognition must remain offline regardless.

## 6. Dataset requirements

- Maintain one shared recording pool with source/license, transcript or label provenance, speaker/voice identity, format and file SHA-256. Functional VAD/VCM/STT/TTS views reference recordings rather than copy them. Use the future single dataset directory/audit document defined in AGENTS.md when its creation is authorized.
- Cover all target categories through versioned additions. Within each, enumerate operations, supported values/units/targets, paraphrases, missing/conflicting parameters, out-of-range values and unknown/out-of-scope speech. Report missing cells rather than using pooled counts to hide gaps.
- Freeze speaker-disjoint train/dev/test splits; deduplicate audio hashes and quarantine conflicting labels. Exclude reserved evaluation/enrollment speakers and calibration recordings as required by the study. Keep natural connected commands distinct from isolated words and room-name proxies.
- Preserve the human-only brightness, parameter and phonetic study rules: original human utterances, no TTS, concatenation, splicing or synthetic audio augmentation. Existing synthetic/mixed studies are separate, explicitly labeled experiments; their existence does not relax a human-only protocol. Keep an untouched human evaluation for synthetic training claims.
- Record subset counts and label quality. Dataset category names, generated prompts, dictionary pronunciations and parser inventories are not independently verified spoken transcripts or acoustic coverage.

## 7. Collective benchmark and individual acceptance evidence

Define the benchmark and quality/resource limits before selecting models. Use development for checkpoint/threshold selection and lock choices in `selection-before-test.json` before held-out scoring. A protocol change after observing test errors requires a new version and preservation of the prior evidence.

| Dimension | Required reporting |
| --- | --- |
| Intent recognition | Per-family precision, recall, F1, confusion counts and sample denominators; separately report all ten use-case categories and missing coverage |
| Complete commands | Exact match of accepted intent, operation and all required typed parameters; per-intent precision/recall, acceptance/abstention rate and denominators |
| Parameters | Per-role/value/target accuracy and joint-command effect; separate isolated words, natural connected numbers, names and conditional evaluations with annotation-supplied roles |
| Rejection | Unknown false-accept rate, known false rejects, ambiguous/conflicting/out-of-range behavior and near-neighbor command confusions |
| Capture robustness | Measured microphone/noise/distance conditions, VAD misses/false triggers, truncation/timeouts and differences between endpointed and full-recording inference |
| Generalization | Held-out speakers, source/accent conditions, label provenance and declared enrollment/catalog conditions; no silent test balancing or tuning |
| Footprint | Total deployed model parameters and bytes, total package/dependency size, peak process memory, load time and CPU usage |
| Speed | On the named physical RPi4/5: identical PCM/thread settings, p50/p95 processing time, real-time factor, and separate speech-end-to-result latency including VAD waiting; disclose warm/cold runs and sample count |
| Standalone behavior | Network-disabled recognition test, no LLM/remote inference dependency, no ASR/STT pipeline or shipped transcription fallback, and artifact/module audit |
| Demo | Actual Pi model/RAM/OS, microphone, commands, installed artifact hashes, successful and failed trials, local behavior and reproducible startup steps |

At minimum, processing must keep pace with audio (real-time factor below 1 on the declared workload); also specify an acceptable p95 response delay so post-utterance batching cannot conceal an unusable interaction. Exact model-byte, RAM, precision/recall, false-accept and response-time targets are **not specified numerically by the supplied brief**. Propose and freeze them with the benchmark before claiming acceptance; do not invent an official limit or select one after seeing test results.

Current default endpoint waiting is 400 ms. Model-only CPU timing excludes disk, speech duration and endpoint waiting; full interaction timing must account for them separately. Desktop ONNX parity, replay tests, parser checks and a valid transfer ZIP are useful evidence, but none is physical Pi or live-microphone validation. Do not count 404 parser checks as 404 successful spoken commands.

## 8. Research priorities and decisions to log

Each experiment must link to the ME/UC IDs it addresses and answer a bounded question:

1. Can finite acoustic heads recover complete commands and connected numeric parameters without transcription, and where do family, slot or acceptance-policy errors dominate?
2. Which missing command categories need a new ontology, original recordings, target enrollment or genuinely new model capacity? Distinguish a data gap from an architectural limitation.
3. What accuracy/abstention/resource tradeoff do compact encoders, keyword models, embeddings or other direct command architectures achieve under the same frozen benchmark? Do not reuse incomparable pooled scores.
4. Can local finite or enrolled vocabularies handle names/contacts reliably under catalog growth and confusable unknowns? Arbitrary free-form reminder/message content remains an explicit unresolved scope problem.
5. Which frontend/export/quantization/decoder choices improve measured Pi cost without degrading per-intent commands or unknown rejection? Any change requiring fresh training/calibration must follow a new or appropriately versioned protocol.
6. What fails in the real microphone/VAD path that is absent in file replay? Use capture evidence before blaming the acoustic model.

At experiment close, record hypothesis, baseline/candidate/version hashes, exact recipe, dataset and selection receipts, per-intent results, resource measurements, failed gates, supported failure attribution, reusable insight and next decision. Mark whether the result is research-only, installed, packaged, device-tested or live-demo-tested. Do not equate those statuses.

## 9. Definition of done and change control

The ME is complete only when the shared dataset and benchmark are documented, the individual tiny VCM is reproducibly trained and evaluated, all required use cases have evidenced coverage (or a user-approved scope revision), standalone inference meets the predeclared quality/resource gates, and a real RPi4/5 demo is measured. An unresolved required slot, missing category, failed gate or unmeasured Pi claim remains visible work.

Update this file when the user changes project scope or new verified implementation evidence changes the gap map. Record the date, affected requirement IDs, reason and evidence. Do not lower requirements to fit a candidate or overwrite historical experiment results. Use AGENTS.md for how to work; use this file for what is being built and what constitutes completion.
