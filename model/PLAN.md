# Phase plan: independent VCM and parameter ASR for Raspberry Pi 4

**Status: original phase plan, now implemented as a measured baseline.** See `IMPLEMENTATION_NOTES.md` for evidence-driven scope changes and `TinyVCM_report.ipynb` for the executed training and evaluation report. Raspberry Pi performance still requires physical hardware measurement.

## 1. Objective and confirmed scope

Build a lightweight voice command model (VCM) that detects the intended command directly from the opening audio. Route the optional parameter portion of the recording to a separately trained automatic speech recognition (ASR) model. Deliver both training pipelines, their public-data manifests, deployment artifacts, a microphone-selectable CLI for Raspberry Pi 4, and a comprehensive executed Python notebook report. Keep this work under `model/`.

The user's latest requirements determine the design:

- Use public datasets; no new speaker recruitment or custom recording campaign is required.
- Train the VCM independently of ASR. It consumes audio and predicts the command; its training must not require transcripts generated by another model, an ASR encoder/checkpoint, or a running ASR service.
- Decide the command as early as the spoken prefix permits, then pass the parameter audio to ASR. ASR supplies argument text and does not choose or change the command.
- Prepare a separate ASR dataset and train the parameter recognizer too. ASR training is a later, independent milestone rather than a prerequisite for VCM training.
- Support English, including Philippine English where public data provides evidence.
- Support configurable names through parameter recognition and an editable catalog, without retraining the VCM for each new name.
- Test deployment on Raspberry Pi 4, with a CLI option for microphone selection.
- Report methodology, real results, limitations, and reproduction steps in `model/TinyVCM_report.ipynb`.

The attached `TinyVCM_design_review.md` is reference material. The implementation follows the user-requested VCM/ASR separation rather than treating every recommendation in that document as a requirement. Home Assistant actuation, music services, wake words, TTS, cloud inference, and a full dialogue manager are outside this phase. The output is a validated command frame, not a claim that an external action occurred.

Environment inspected on 2026-09-15: this repository initially contains only a README and Python `.gitignore`. The workstation reports an RTX 4080 SUPER with 16,376 MiB VRAM and approximately 192 GiB free on C:. CUDA compatibility and training speed still require a probe. Pi RAM, OS, microphone, and actual runtime performance remain unverified.

## 2. System contract and early decisions

```text
microphone / WAV -> 16 kHz audio + bounded ring buffer
                        |
                 causal VCM, continuously
                        |
              intent + readiness + parameter boundary
                        |
              intent event emitted before speech ends
                        |
             parameter audio retained from the buffer
                        |
          separate ASR, only if parameters are present
                        |
        deterministic argument parser + editable catalog
                        |
           accepted / rejected / needs_clarification
```

The VCM also works with ASR disabled: it emits the command ID, confidence, timestamps, and a parameter-slice reference. This is a useful standalone deliverable and must have its own evaluation and CLI mode.

### Command-first grammar

Early detection is possible only after the action is distinguishable. For example, `turn on ...` identifies power-on; `set ...` alone does not distinguish volume, brightness, or a timer. Train a `WAIT` state for incomplete/ambiguous prefixes. Declare supported command-first patterns; parameter-first or late-disambiguated sentences must be evaluated separately and must not be counted as successful early decisions.

Proposed first vocabulary, subject to the public-data coverage audit:

| VCM command | Distinguishing prefix example | ASR parameter tail | Final frame |
|---|---|---|---|
| `POWER_ON`, `POWER_OFF` | turn on / turn off | device name or area/kind | `SET_POWER(target, on)` |
| `BRIGHTNESS_SET` | set the brightness of | device name + percentage | `SET_BRIGHTNESS(target, percent)` |
| `BRIGHTNESS_UP`, `BRIGHTNESS_DOWN` | brighten / dim | device name + optional amount | `ADJUST_BRIGHTNESS(target, delta_percentage_points)` |
| `COLOR_SET` | change the color of | device name + color | `SET_COLOR(target, color)` |
| `VOLUME_SET` | set the volume to | percentage | `SET_VOLUME(percent)` |
| `MEDIA_PLAY` | play | optional title/artist/playlist from a bounded catalog | `PLAY(...)` |
| `MEDIA_PAUSE`, `MEDIA_RESUME`, `MEDIA_STOP` | pause the music / resume the music / stop the music | none initially | `PAUSE()`, `RESUME()`, `STOP_MEDIA()` |
| `TIME_QUERY`, `DATE_QUERY` | what time is it / what is the date | none initially | `GET_TIME()`, `GET_DATE()` |
| `TIMER_SET` | set a timer for | duration | `CREATE_TIMER(duration_s)` |

This is 14 VCM classes, plus readiness/rejection states. The two power classes fix the Boolean value in the VCM output; ASR does not infer on/off. The same rule applies to brighten/dim. Fan power can share power commands when source examples support it; fan-speed control is a documented coverage gap until suitable labeled public audio is found. Audit timer examples separately from alarms. Do not rename an alarm intent to timer merely to populate the class.

Keep `coverage.json` with, for each class and pattern, available training/development/test counts, required/optional slots, early-routing eligibility, and supported/insufficient-data status. Implement a class only when it has defensible real examples; retain absent classes in the report as gaps. Public text templates alone do not establish acoustic support. This is a proposed initial scope, not a promise to cover the review's entire assistant catalog.

### Routing and output behavior

1. Capture audio continuously into a bounded 8-second utterance buffer. Process causal VCM chunks every 40 ms, with a shared 10 ms feature hop. Preserve original sample indices through resampling.
2. Emit an intent event after the command probability and readiness pass development-calibrated thresholds for an initial 120 ms stability interval. This is a recognition event, not permission to execute an incomplete utterance.
3. Predict the transition into the parameter tail separately from the intent timestamp. These are different quantities. Retrieve audio from the estimated boundary with an initial 150 ms look-back; do not simply start the slice when the intent event is emitted.
4. Continue collecting the tail until endpointing, initially 400 ms trailing silence. Tune on development audio with paused names/numbers. Use 200 ms pre-roll and reject speech that exceeds the 8-second limit rather than executing a truncated fragment.
5. For the first ASR implementation, decode the completed parameter tail once. Sending/retaining that tail starts after intent detection; final argument text can arrive after speech ends. The VCM remains streaming even when ASR is utterance-based.
6. Skip ASR for commands with no parameters. With ASR disabled, return `needs_parameters` and the slice metadata for parameterized commands. A missing required parameter never becomes a guessed default. `PLAY()` may use a declared default only when the command contract explicitly allows it.
7. Parse ASR text with the already-selected command's argument grammar. Normalize numbers/durations/colors, match allowed catalog names, and reject unknown or ambiguous matches. An ASR hypothesis may fill slots or cause rejection; it cannot change `POWER_ON` into `POWER_OFF` or select a different action.
8. Emit final command output after endpointing and validation. Reject unsupported compounds, cancellations, and incomplete requests where detected; benchmark these explicitly. If a later contradiction invalidates an early decision, retract that candidate rather than reporting early intent as completed action.

Example handoff for `turn on Aurora lamp`: VCM chooses `POWER_ON`; the retained parameter tail contains `Aurora lamp`; ASR transcribes the tail; catalog grounding returns `SET_POWER(target=light.aurora, on=true)`. Runtime-enrolled names affect ASR decoding/grounding context, never the VCM label inventory or weights. Preserve display names separately from normalized matching forms.

### Critical issue: timestamps without an ASR dependency

The inspected SLURP format gives transcript tokens, entity spans, recording IDs, and metadata, but not ready-to-use time boundaries for the parameter audio. Text spans must not be converted to seconds by proportional word counts. Energy-based VAD identifies speech/silence, not the boundary between a command and a name. [SLURP annotation format](https://github.com/pswietojanski/slurp)

Prepare a bounded timestamp annotation set **from existing public recordings**, using waveform/audio review and supplied human transcripts. This requires annotation work, not collection of new voices and not an ASR model. Do not quietly introduce Whisper, a pretrained CTC aligner, or forced-alignment checkpoints into the VCM pipeline.

For each selected recording mark:

- The earliest time at which the spoken prefix actually distinguishes the command (`intent_ready_ms`).
- The start of the parameter-bearing tail (`parameter_start_ms`), or an explicit no-parameter label.
- The tail transcript including intervening words, such as `Aurora lamp to thirty percent`; individual slot values and their original text spans are additional labels.
- Speech endpoint, uncertainty around each boundary, early-routing eligibility, and annotation/review provenance.

Start with roughly 500 verified recordings distributed across classes, speakers, phrase patterns, and split assignments; expand toward 2,000 if boundary/readiness learning or evaluation needs it. These are work estimates, not available counts or guaranteed sufficiency. Independently review a stratified sample and report timing disagreement. Use uncertain rows for utterance-level intent training if appropriate, but mask their timing losses. Never claim validated early routing from full-utterance labels alone.

For ASR training, use whole public utterances initially, then fine-tune on verified tails. The VCM must not wait for ASR training to obtain its labels. An ASR-generated alignment can be a later optional study only; it is not in the baseline dependency graph. If timestamp annotation is unfinished, whole-utterance VCM training may proceed, while early-decision and audio-slice acceptance remain explicitly pending.

## 4. Train the standalone VCM first

### Architecture and labels

Use a small causal depthwise separable temporal CNN with an intent head, a readiness/rejection head, and a parameter-boundary head. This is acoustic classification plus timing; it has no phoneme/character transcription head and no ASR-pretrained weights. A MatchboxNet-style encoder is a compact starting point, but prefix routing is a new task requiring its own evidence. [MatchboxNet paper](https://arxiv.org/abs/2004.08531)

Initial VCM configuration:

- 16 kHz mono; 40 log-Mel bins; 25 ms Hann window; 10 ms hop; FFT 512; fixed Mel convention/frequency range/log floor; training-only normalization statistics. Reuse the same frontend implementation in training, replay, and microphone inference.
- Stem width 128; five residual blocks with two depthwise-separable layers at width 128, kernels 5/7/9/11/13, and causal padding. Measure receptive field and parameter count; target 0.2-0.5 million parameters, hard cap 1 million.
- Explicit convolution state and causal running pooling/state for intent evidence. No centered padding, future frames, whole-utterance normalization, or final global pooling may leak future information into early outputs. Test chunked output against causal full-sequence replay.
- Frame/chunk labels are `WAIT` before sufficient evidence, command-ready after a verified cue, and parameter transition at its annotated time. No-parameter commands have a separate mask/state. The model must be able to reject noncommands and insufficient speech.

### Training and selection

1. Warm-start from random weights on full SLURP audio with valid utterance-level command labels. This establishes the classification baseline; its scores are not early-decision scores.
2. Fine-tune on causal prefixes/streams using verified timing labels. Only expose audio available at each training step. Sample ambiguous prefixes and hard negatives as well as correctly completed cues; prevent the model from relying on a distinctive name at the end of a command.
3. Initial objective: masked intent cross-entropy + 0.3 readiness/rejection loss + 0.3 boundary loss. Mask absent/uncertain timing labels, normalize by eligible examples, and report each term separately.
4. Start AdamW at 1e-3, weight decay 1e-4, gradient clipping 1.0, dropout 0.1, 5% warm-up/cosine decay, length-aware batching, and up to 50 epochs with patience 8. Profile a first epoch before estimating GPU hours.
5. Augment only training audio with gain, 5-20 dB noise, room responses, and modest 0.9-1.1 speed perturbation. Transform timing annotations exactly under speed/resampling and account for room-response onset; retain clean examples and short negation/numeric cues.
6. Develop with seed 17. Compare full-utterance baseline versus causal prefix model, then boundary look-back and trigger stability settings on development data. Run seeds 17/29/43 for the chosen recipe if practical; otherwise label single-seed results explicitly.
7. Select using early intent accuracy, premature-trigger rate, latency after the earliest sufficient cue, and parameter retention together. Freeze the VCM before the final end-to-end experiment.

Required independence check: VCM preparation, training, export, evaluation, and `--asr off` inference work with every ASR artifact absent. No ASR import/model load or ASR transcription appears in this path. Unit-test that changing ASR output cannot alter an already-selected command ID.

## 5. Train the parameter ASR separately

The ASR receives only the parameter-bearing tail plus deliberate boundary context. It returns text and recognition scores, not an intent. General transcript audio may be used to train its acoustic/language units; runtime use stays restricted to parameter slices.

- Train a separate small character-CTC temporal CNN from random initialization, using a compact QuartzNet-inspired architecture. Start with six blocks of three separable layers at width 256, a stride-2 stem, and an approximately 1.5-3 million parameter target; hard cap 5 million. Exact count/compute are measured before long training. Published QuartzNet results are architectural evidence, not expected accuracy for this smaller model. [NVIDIA ASR model documentation](https://docs.nvidia.com/nemo-framework/user-guide/26.02/nemotoolkit/asr/models.html)
- Start with a normalized English character inventory: letters, space, apostrophe, CTC blank, and explicit normalization rules. Preserve display spelling outside the recognizer. Character output supports new spellings without a fixed class per name, but arbitrary proper-name recognition still requires measured evidence.
- Stage A: LibriSpeech `train-clean-100` -> `dev-clean` selection. Stage B: real SLURP transcripts, verified parameter tails, and suitable public Philippine English audio. Retain an acoustic-data mixture to reduce forgetting. Keep split assignments consistent with the VCM.
- Use CTC loss, AdamW starting near 1e-3, gradient clipping, warm-up/decay, length-aware batches, and up to 50 epochs per stage with patience 8. Profile 60 seconds of audio per batch as an initial VRAM budget, adjust from measurement, and record the effective batch size. Compute CTC in FP32 if mixed-precision stability requires it.
- Select ASR checkpoints using development tail word/character error and normalized slot exact match. Compare general-speech-only training against parameter-tail adaptation. Public whole-utterance scores are a diagnostic, not the deployment score.
- Begin with greedy character decoding; evaluate a small beam (16/32) and command-specific parameter constraints on development data. Catalog bias may help name recognition, but keep unconstrained alternatives and unknown-name rejection so an unseen word is not automatically replaced by the nearest registered device.
- Handle a multi-slot tail such as `Behind the Curtain by Misamo` with the already-selected `MEDIA_PLAY` parser. Do not split on arbitrary silence between each slot. Verify that command context included by look-back is represented in training labels and consistently removed only by the selected command's parser.
- Produce separate ASR checkpoints, exports, configuration, vocabularies, metrics, and data manifests. No end-to-end gradient dependence on the ASR is added to VCM training in this phase.

Both models can learn the same frontend convention, while retaining separate normalization/configuration artifacts if their training distributions require it. The final catalog stores stable IDs, aliases, kinds, and capabilities. Numeric ranges, required slots, unknown names, and ambiguous aliases are checked after transcription; they never become extra VCM name classes.

## 7. Raspberry Pi export and CLI

Use Raspberry Pi OS 64-bit and an ARM64 Python 3.12 environment with ONNX Runtime CPU, NumPy/SciPy, SoundFile, and sounddevice/PortAudio. Keep PyTorch/CUDA and notebook dependencies in the workstation group. ONNX Runtime 1.30.0 currently publishes a CPython 3.12 ARM64 wheel requiring glibc 2.28 or newer; installation and operator support still need a Pi probe. [Published runtime wheels](https://pypi.org/project/onnxruntime/)

Export FP32 ONNX first, starting with opset 17. The streaming VCM export includes explicit cache/state inputs and outputs; the ASR may accept a variable-length completed tail. Verify frontend/logit tolerances, causal cache reset, decoded outputs, and timing alignment on development fixtures. Then calibrate static INT8 for each CNN using representative training-only audio. Start with per-channel weights and S8S8 QDQ. Measure accuracy and ARM latency before choosing the deployment format; ship FP32 for a component if INT8 regresses it. [ONNX quantization guidance](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)

The deployment bundle contains separate VCM and ASR files, frontend statistics, vocabularies, thresholds, command/parameter schemas, catalog example, runtime version lock, licenses, and SHA-256 hashes. Report both models, decoding assets, buffers, and process memory in the total footprint. Enrolling names must preserve both neural hashes. ASR stays unloaded in ASR-off mode.

### Planned CLI

These commands are implementation targets, not currently implemented commands. Run from `model/` after installation:

```bash
python -m tinyvcm prepare --task vcm --config configs/data.toml
python -m tinyvcm train-vcm --config configs/vcm.toml
python -m tinyvcm prepare --task asr --config configs/data.toml
python -m tinyvcm train-asr --config configs/asr.toml

python -m tinyvcm devices
python -m tinyvcm listen --bundle artifacts/tinyvcm --asr off --mic 2
python -m tinyvcm listen --bundle artifacts/tinyvcm --asr on --mic "USB Audio" --host-api ALSA
python -m tinyvcm listen --config configs/pi4.toml
python -m tinyvcm predict --bundle artifacts/tinyvcm --asr on --wav samples/command.wav
python -m tinyvcm benchmark --bundle artifacts/tinyvcm --manifest data/manifests/pi_test.jsonl --output reports/pi4.json
```

Microphone contract:

- `devices` lists input-capable devices, index/name/host API, available channels, default rate, and default-input marker without loading either model.
- `--mic` accepts the current device index or an unambiguous name; `--host-api` disambiguates backends. CLI options override TOML, then the OS default. Print the resolved choice; never silently pick the first ambiguous match.
- Persist device name plus host API because indices may change after reboot. Support zero-based `--channel` and optional `--capture-rate`.
- Validate input settings. Prefer native mono 16 kHz; otherwise capture a supported rate, select the configured channel, and resample while preserving the timestamp mapping. Do not relabel 48 kHz audio or implicitly average array channels.
- Keep callback work limited to moving audio into a bounded queue. Run VCM/ASR outside it. Detect overflow, missing/output-only devices, unsupported forced rates, timeout, and disconnection; invalidate affected utterances. Ctrl+C closes the stream cleanly.
- Emit JSON intent/parameter/final events with sample timestamps on stdout and hardware diagnostics on stderr. ASR-off output indicates unresolved parameters rather than fabricating argument values.

Use `query_devices`, `query_hostapis`, `check_input_settings`, and explicit `InputStream(device=...)`. [sounddevice device APIs](https://python-sounddevice.readthedocs.io/en/latest/api/checking-hardware.html), [stream APIs](https://python-sounddevice.readthedocs.io/en/latest/api/streams.html)

## 8. Evaluation and proposed acceptance targets

Freeze each model, its preprocessing, trigger/boundary thresholds, parser/catalog rules, and decoder settings before final testing. Test predicted slices as well as oracle annotated slices to separate boundary errors from ASR errors. Use the same frozen audio across FP32/INT8 comparisons. All numerical targets below are proposals, not measured results.

| Component | Measurements and initial targets |
|---|---|
| VCM independence | Data preparation/training/export/inference succeeds with ASR absent; no transcript input at inference and no pretrained ASR components in training. Mandatory. |
| VCM intent | Macro F1, per-class recall/confusion, unknown rejection; target at least 95% clean accuracy on the declared supported set. Report whole-utterance baseline separately. |
| Early recognition | Time from earliest sufficient cue to stable intent; target P95 at most 300 ms. Report fraction emitted before speech end, before parameter onset, and after parameter onset, plus accuracy at each latency. No early target for a pattern whose decisive evidence is late. |
| Premature/wrong triggers | Trigger rate before the annotated cue and wrong-intent rate; initial target at most 1% on at least 500 labeled ambiguous-prefix/negative examples. Report valid-command rejection alongside this rate. |
| Parameter slicing | Signed start-time error, phonetic onset retention, clipped-tail rate, extra prefix audio, and empty-tail false routing. Initial target at least 99% first-parameter onset retention on the annotated test set; disclose uncertainty and padding cost. |
| ASR | Tail WER/CER, exact parameter text, normalized slot accuracy, and unknown-name behavior; initial supported-slot exact-match target at least 90% on clean verified tails. Report oracle versus predicted slices and greedy versus catalog-biased decoding. |
| Complete command | Exact action + all normalized arguments + grounded target set. Initial targets 90% clean and 80% on a precisely specified noisy replay set. Include errors from VCM, slicing, ASR, parsing, and grounding. |
| New names | Alias-held-out and strict novel-word results with 25/100/500 catalog sizes; unchanged VCM/ASR hashes for enrollment. Report correct target, wrong target, rejection, and ambiguity separately. |
| Philippine English | Per-source/task speaker counts and results. Missing public command coverage is marked unverified; read-speech ASR results cannot satisfy a command-accuracy claim. |
| Quantization | At most 1 percentage point absolute degradation in each component's primary accuracy and the complete-command metric; preserve boundary/rejection contracts. |
| Pi compute | VCM processing P95 below the 40 ms chunk interval; ASR real-time factor below 1, initial target at most 0.5. RTF is processing seconds divided by audio seconds. Measure decoding and total processing too. |
| Pi response | P50/P95 speech-end to final JSON, including endpointing and ASR; initial P95 target at most 1.5 s for tails up to 3 s. Report longer tails separately through the utterance limit. |
| Size/stability | VCM at most 1M parameters; ASR at most 5M. Initial total process RSS target below 400 MiB. Measure both loaded and VCM-only modes; 30-minute live capture with CPU/RSS/temperature/throttling and overflow logs. |
| Microphone selection | Actual Pi checks for default/index/name, ambiguity, missing/output-only devices, sample-rate conversion, channel selection, and unplug/replug. |

Report sample counts and confidence intervals, grouped by speaker where feasible. A small or unbalanced accent subset limits the claim. No wake-word false activation metric applies here, and a short capture run cannot establish a low long-term false-command rate.

Record Pi model/RAM, OS/architecture, Python/runtime versions, cooling/governor, thread count, microphone/host API/rate/channels, audio duration, catalog size, and both model hashes. Tune 1/2/4 inference threads using development runs; separate cold-start, warm latency, VCM-only, and combined-system measurements. Prerecorded public data provides repeatable recognition tests. Actual microphone capture validates the hardware path; it is not added to the training set or presented as a new dataset.
